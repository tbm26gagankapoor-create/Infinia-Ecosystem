LLMOps PRD

A comprehensive product requirements document for the Corerun LLMOps Console — covering current capabilities, feature gaps, roadmap, and the path to a production-grade LLM operations platform.

Vision & Strategic Goals

Vision Statement

A unified, Kubernetes-native LLMOps platform that manages the full lifecycle of LLM inference — from model deployment and routing to observability, evaluation, and governance.

Unified Operations
One console to deploy, monitor, evaluate, and govern all LLM workloads across clusters and teams.
GitOps-First
Declarative model deployments versioned in Git with automatic reconciliation to Kubernetes.
Quality & Safety
Built-in guardrails, evaluation frameworks, and tracing to ensure LLM outputs are safe and reliable.
Cost Transparency
Full cost attribution per request, model, team, and application with GPU utilization optimization.
Developer Velocity
Deploy a model in under 5 minutes. Rollback in under 30 seconds. Test prompts in the built-in playground.

Problem Statement

Platform teams running LLM inference at scale face fragmented tooling: separate dashboards for deployment (Kubernetes), monitoring (Prometheus/Grafana), prompt management (spreadsheets), evaluation (notebooks), and cost tracking (cloud billing). This fragmentation leads to slow iteration cycles, invisible quality regressions, uncontrolled costs, and safety incidents. Corerun LLMOps unifies these workflows into a single platform purpose-built for LLM operations.

OR1. Model Import & Onboarding P0
Why This Matters

Without a structured import pipeline, models enter the registry without validation, test inference, or license checks. This leads to broken deployments, OOM crashes from incorrect memory estimates, and potential legal exposure from restricted model licenses.

Required Import Parameters
  • Model ID — Alphanumeric + hyphens, max 64 chars, must be unique across registry
  • Engine Type — Enum: vLLM, Ollama, SGLang, TGI, Whisper, Piper
  • Architecture — Enum: LLaMA, Mistral, Qwen, Falcon, MPT, GPT-NeoX, Whisper, VITS, etc.
  • Quantization Format — Enum: FP16, BF16, INT8, INT4, GPTQ, AWQ, GGUF, None
  • Context Length — Range: 512–1,048,576 tokens. Must not exceed engine maximum
  • Tensor Parallelism — Must be power-of-2 and ≤ available GPU count
  • GPU Memory Requirement — Estimated GB per GPU. Cross-checked against actual node capacity
  • Model Source URI — HuggingFace repo ID, S3/GCS path, OCI image, or Git LFS pointer
Optional Parameters
  • System prompt template (max 4,096 chars)
  • Tokenizer configuration path or HuggingFace tokenizer ID
  • Custom stop tokens (max 16 tokens)
  • Max batch size and max concurrent requests
  • Chat template (Jinja2 format) for instruction-tuned models
  • Estimated tokens/second throughput (used for capacity planning)
  • Description, tags, and owner team assignment
Validation Rules
  • Model ID uniqueness enforced at database level
  • Engine–architecture–quantization compatibility checked against OR4 matrix
  • Context length validated against engine-specific maximums
  • Tensor parallelism must be power-of-2 and ≤ GPU count in target namespace
  • GPU memory cross-check: estimated ≤ available node capacity + 10% buffer
  • Source URI reachability verified (HTTP HEAD or API metadata call)
  • All string inputs sanitized against injection attacks
Import Sources
  • HuggingFace Hub — Resolve repo, read model card, auto-detect architecture and quantization from config.json
  • S3 / GCS Bucket — Verify IAM access, list files, validate expected directory structure
  • OCI Registry — Pull manifest, verify layer integrity, extract model metadata
  • Git LFS — Clone metadata only, verify LFS pointers resolve, validate file sizes
  • Each source adapter returns a normalized metadata object for the import pipeline
Import Workflow Pipeline
  1. Validate Parameters — Run all validation rules. Block on any failure with specific error messages
  2. Download to Staging — Pull model weights to staging PVC. Progress reported via WebSocket. Supports resume on network failure
  3. Checksum Verification — SHA-256 checksum of all downloaded files vs manifest
  4. Format Validation — Verify config.json, tokenizer files, shard count, and weight file structure
  5. Test Inference — Spin up ephemeral single-replica K8s Job. Run 3 canary prompts. 10-minute timeout. Must produce non-empty, non-error responses
  6. Register — Write to model registry with all metadata, mark as “Available”

Pipeline is resumable — on failure, retry resumes from the last successful step.

License Compliance
  • Auto-detect license from model card or LICENSE file in source repository
  • Classify: Permissive (Apache, MIT), Copyleft (GPL), Restricted (LLaMA Community, Gemma Terms), Unknown
  • Configurable policy per organization: block, warn, or allow restricted licenses
  • Restricted license deployments require explicit acknowledgment with audit trail
  • License metadata stored in registry and visible on model detail page
Success Metrics
  • 100% of registered models have passed test inference
  • >90% import wizard completion rate (no abandonment)
  • Zero restricted-license deployments without acknowledgment
  • Import time <15 minutes for models under 30 GB
OR2. Capacity Management & Admission Control P0
Why This Matters

Without admission control, teams deploy models that exceed available GPU capacity, causing OOM kills, cascading failures, and noisy-neighbor problems. Priority queueing and burst capacity ensure critical workloads always get resources while experiments don’t starve.

Admission Controller
  • Kubernetes ValidatingAdmissionWebhook evaluating GPU and memory quotas before pod creation
  • Reject with actionable message: “Requested 4× A100 but namespace has 2 available (2 reserved by team-ml)”
  • Check both GPU count and GPU memory against namespace quotas and cluster capacity
  • Every admission decision (accept/reject) logged in audit trail with actor, timestamp, and reason
Priority Queue System
  • Critical — Production workloads. Guaranteed SLA. Never preempted
  • Standard — Dev/staging workloads. Best-effort fair scheduling. Never preempted by Standard
  • Best-Effort — Experiments and batch jobs. Preemptable by Critical when capacity is constrained
  • FIFO ordering within each priority class
  • Queue depth and estimated wait time visible in deployment UI
  • Configurable max queue depth (default 50). Reject with 429 on overflow
Workload Preemption
  • Critical workloads can preempt Best-Effort on the same GPU type when no free capacity exists
  • 30-second graceful drain period before termination. In-flight requests allowed to complete
  • Preempted workloads re-queued automatically at head of their priority class
  • Preemption events trigger notification to workload owner via configured channels
  • Opt-out flag for specific Best-Effort workloads (e.g., long-running fine-tune jobs)
Capacity Forecasting
  • Linear regression on GPU allocation trends over 7-day, 30-day, and 90-day windows
  • Forecast dates for 80%, 90%, and 100% capacity exhaustion per GPU type
  • Weekly capacity report emailed to cluster administrators
  • Alert when any GPU type forecasted to exhaust within configurable horizon (default 14 days)
  • Cloud burst cost estimate shown alongside on-prem exhaustion forecast
GPU Reservation System
  • Reserve GPU slots up to 7 days in advance for planned deployments
  • Reservations count against namespace quota but are not allocated to pods until claimed
  • Auto-expire if unclaimed within configurable window (default 4 hours)
  • Calendar view in UI showing reservations by team, GPU type, and time window
  • Conflict detection prevents double-booking beyond available capacity
Burst Capacity
  • Overflow to cloud GPU providers (Lambda, CoreWeave, RunPod, AWS) when on-prem capacity exhausted
  • Per-namespace configuration: allowed providers, max GPU count, max cost per hour
  • Auto-provision via provider API when admission controller detects on-prem full + burst enabled
  • Auto-terminate cloud instances when on-prem capacity frees up or max duration reached (default 24h)
  • Full cost tracking with team attribution. Cloud GPU hours billed separately in cost dashboard
Success Metrics
  • Zero GPU over-subscription incidents
  • Critical workloads scheduled within 5 minutes (P99)
  • Standard workloads wait <30 minutes (P90)
  • Capacity forecast accuracy within ±10% at 14-day horizon
  • Burst capacity provisioned within 10 minutes
OR3. Dynamic Compute Inventory System P0
Why This Matters

GPU fleets are expensive and opaque. Without real-time inventory tracking, teams can’t answer basic questions: How many GPUs are free? Are any failing? Who’s using what? Orphaned pods and zombie deployments silently waste capacity that could serve production workloads.

Real-Time GPU Fleet Dashboard
  • Per-Node View — Hostname, GPU type (A100, H100, L40S…), GPU count, allocated vs total, temperature, power draw, driver version
  • Per-GPU View — GPU index, PCI bus ID, allocated deployment name or “free”, memory used/total, ECC error counts
  • Cluster-Wide View — Totals by GPU type, allocated/free/maintenance breakdown, utilization heatmap
  • Filterable by GPU type, node label, allocation status, health status
  • Auto-refresh at 10-second intervals with configurable polling
Inventory Reconciliation
  • Orphaned Pods — Detect pods with GPU requests but no corresponding LLMOps deployment record
  • Zombie Deployments — Detect deployments marked “Running” in database but with zero live pods in K8s
  • Leaked GPU Memory — Detect nvidia-smi showing memory use with no matching pod on the node
  • Reconciliation scan runs every 5 minutes via background goroutine
  • Dashboard shows discrepancies with one-click cleanup actions (delete orphan, mark zombie as Error, reset leaked GPU)
Maintenance Windows
  • Operator marks node for maintenance via UI or API
  • Platform drains workloads to other nodes respecting GPU affinity and anti-affinity rules
  • Progress indicator: N/M pods migrated, estimated time remaining
  • Node returns to available pool only after passing health check (GPU functional, driver loaded, NVML responsive)
  • Scheduled recurring maintenance windows (e.g., Sunday 2–4 AM) with pre-emptive migration starting 30 minutes before
GPU Health Monitoring
  • ECC correctable and uncorrectable error counts tracked via NVML
  • Immediate alert on uncorrectable ECC errors (data corruption risk)
  • Thermal throttling alert when GPU sustains throttled state for >5 minutes
  • Clock frequency downclocking detection and alerting
  • Fan speed and power draw anomaly detection
  • Auto-quarantine: GPU removed from scheduling pool when health score drops below configurable threshold
Allocation Policies
  • Bin-Packing — Pack onto fewest nodes. Frees entire nodes for large multi-GPU deployments
  • Spread — Distribute across nodes for fault isolation. Recommended for Critical workloads
  • GPU Affinity — Co-locate multi-GPU deployments on the same node for NVLink/NVSwitch interconnect
  • NUMA Awareness — Schedule on CPU sockets with direct PCIe affinity to allocated GPUs
  • Configurable per-namespace or per-deployment. Default: bin-packing for Best-Effort, spread for Critical
Inventory Alerts
  • Low capacity warning when free GPUs of any type fall below configurable threshold
  • Hardware failure alert on GPU quarantine event
  • Thermal event alert on sustained throttling
  • Orphan/zombie detection alert on reconciliation discrepancies
  • All alerts routed via FG9 notification channels (Slack, PagerDuty, webhooks)
Historical Utilization Reports
  • Weekly and monthly reports per-team, per-GPU-type, per-node
  • Peak vs average utilization with idle percentage highlighted
  • Cost attribution by GPU-hours consumed per team
  • 30/60/90-day trend lines for capacity planning
  • Export as CSV. Data feeds into OR2 capacity forecasting module
Success Metrics
  • 99.9% inventory accuracy (dashboard matches reality within 30 seconds)
  • Orphaned resource cleanup within 10 minutes of detection
  • Zero dropped requests during planned maintenance migrations
  • GPU failure detected and quarantined within 60 seconds
  • Idle GPU rate reduced 20% within 3 months of deployment
OR4. Pre-Deployment Safety & Validation P1
Why This Matters

Production deployments that fail on launch waste GPU capacity, block the deployment pipeline, and erode team confidence. Pre-flight checks, canary deployments, and approval gates catch issues before they affect users or consume scarce compute resources.

GPU Memory Pre-Flight
  • Estimate GPU memory requirement: (params × bytes_per_param / quant_ratio) + kv_cache_overhead + runtime_overhead
  • Compare estimated memory against available node capacity from OR3 inventory
  • Block deployment if estimated memory exceeds available by more than 10% safety buffer
  • Show detailed breakdown in deployment wizard: weights, KV cache, activations, runtime
Model–Engine Compatibility Matrix
  • Matrix of engine × architecture × quantization format with status: Supported, Untested, Unsupported
  • Block deployments with unsupported combinations. Warn on untested with user acknowledgment
  • Stored in PostgreSQL, editable by cluster administrators
  • Auto-populated from test inference results in OR1 import pipeline
Canary Deployment
  • Route configurable percentage of traffic (default 5%) to new revision via Envoy weighted clusters
  • Monitor canary for evaluation window (default 15 minutes): error rate, latency P50/P99, output quality
  • Auto-promote to 100% if all metrics pass thresholds
  • Auto-rollback if any metric breaches threshold during evaluation window
  • Manual override: operator can force promote or rollback at any time
Deployment Dry-Run
  • Validate Helm chart renders without errors
  • Check RBAC permissions for the target namespace
  • Verify container image is pullable (HTTP HEAD to registry)
  • Confirm GPU resource requests match available node selectors and tolerations
  • Return structured pass/fail report with specific failure reasons
  • Available via API (POST /api/v1/deployments/dry-run) and in the deploy wizard UI
Approval Gates
  • Configurable per-namespace: require N approvals before production deployment proceeds
  • Approval requests sent via Slack, email, or webhook with deployment details
  • Configurable expiry timeout (default 24 hours). Expired requests must be re-submitted
  • Break-glass bypass for emergencies with mandatory justification and full audit trail
  • Integrated with FG7 RBAC roles: only designated approvers can approve
Rollback Artifact Safety
  • Before initiating rollback: verify container image exists in registry, model weights accessible, Helm values stored
  • Block rollback and alert operator if any required artifact is missing
  • Configurable retention: keep last N revision artifacts (default 5)
  • Retention policy respects “pinned” revisions that are never garbage-collected
Success Metrics
  • Zero OOM deployment failures after pre-flight check enablement
  • 95% first-attempt dry-run pass rate (measure deployment quality improvement)
  • Canary catches 100% of regressions exceeding configured thresholds
  • Approval turnaround <1 hour during business hours
OR5. Model Failure Handling & Recovery Backlog
Why This Matters

When a model fails mid-serving, every second of undetected failure means lost requests and degraded user experience. Automatic detection, classification, and recovery transforms model failures from emergencies into managed events.

Health Probes
  • Liveness Probe — K8s probe on /health. Restarts pod after 3 consecutive failures (configurable). Timeout 5s, period 10s
  • Readiness Probe — Probe on /ready verifying model is loaded and accepting requests. Pod removed from Service endpoints when unhealthy
  • Startup Probe — Extended failure threshold of 30 (5-minute window) for large 70B+ models. Prevents liveness probe from killing slow-loading models
Inference Health Check (Canary Requests)
  • Background synthetic inference requests with configurable prompt and expected latency threshold
  • Runs every 30 seconds per deployment
  • Detects silent model corruption where /health returns 200 but inference quality has degraded
  • Alerts when canary latency exceeds 3× baseline or output is empty/malformed
Automatic Rollback Triggers
  • Error rate exceeds configurable threshold (default: 10% over 5-minute window)
  • P99 latency exceeds 3× the rolling 1-hour baseline
  • OOM kill detected via pod termination reason
  • GPU ECC uncorrectable error count exceeds threshold
  • Canary inference produces empty or error responses 3 times consecutively
  • All thresholds configurable per-deployment. Triggers can be individually enabled/disabled
Rollback Execution
  • When trigger fires: freeze current revision, initiate rollback to last-known-good revision
  • Verify previous revision artifacts exist (container image, model weights, Helm values) via OR4 safety check
  • Rolling update strategy: new pods healthy before old pods terminate
  • If artifacts missing: alert operator, block automatic rollback, escalate to on-call
Failure Classification Engine
  • Transient — Retry with exponential backoff (max 3 attempts). Examples: network timeout, temporary GPU memory spike
  • Permanent — Trigger rollback and page on-call. Examples: model corruption, incompatible config, persistent OOM
  • Capacity — Queue request and attempt reschedule to different node. Examples: GPU memory fragmentation, node pressure
  • Classification based on error code, pod termination reason, and GPU health status
  • Configurable as YAML rules for extensibility. Stored in deployment event log
Graceful Degradation
  • On failure detection: mark endpoint as draining, stop accepting new connections
  • Allow in-flight requests up to 30-second timeout to complete
  • Shift traffic to healthy replicas or failover provider (via OR6) before teardown
  • If no healthy replicas available: return 503 with Retry-After header
Incident Timeline Reconstruction
  • Aggregate deployment events, probe status changes, metric anomalies, and rollback actions into unified timeline
  • Millisecond-precision timestamps for all events
  • Exportable as JSON for integration with PagerDuty, Jira, or post-mortem tools
  • Visual timeline view in deployment detail page
Success Metrics
  • Mean Time to Detect (MTTD) <30 seconds
  • Auto-rollback MTTR <2 minutes
  • Zero undetected silent model corruption per quarter
  • 95% correct failure classification rate
OR6. Provider Resilience & Failover Backlog
Why This Matters

External LLM providers experience outages, rate limits, and degraded performance. Without circuit breakers and failover chains, a single provider issue cascades into application-wide failures. Provider resilience ensures end-to-end availability even when individual providers are down.

Circuit Breaker Pattern
  • Per-provider-endpoint state machine: Closed (normal) → Open (fail-fast) → Half-Open (probe)
  • Open after N failures (default 5) or error rate >X% (default 50%) in Y-second window (default 60s)
  • Half-Open: single probe request every Z seconds (default 30s). Success returns to Closed
  • All thresholds configurable per provider. State transitions logged with timestamps
Automatic Failover Chains
  • Ordered failover per model: primary → secondary → tertiary
  • Example: OpenAI GPT-4 → Azure OpenAI GPT-4 → self-hosted Llama-3 70B
  • Triggered automatically when primary provider’s circuit opens
  • Configurable per-model or per-application
  • Auto-failback when primary circuit returns to Closed state
  • Option for manual failback on critical workloads (prevents flapping)
Provider Health Scoring
  • Composite score 0–100: latency P50 vs baseline (30% weight), error rate (40%), availability (30%)
  • Score below threshold (default 40) triggers circuit open
  • Displayed on Provider dashboard with trend sparkline
  • Health history stored for SLA tracking and vendor management
Degraded Mode
  • When all providers unavailable: optionally serve cached responses for identical prompts
  • Cache keyed on prompt hash + model + temperature. Configurable TTL (default: disabled)
  • Responses tagged with X-Served-From: cache header for client awareness
  • Fallback to smaller/cheaper model on cache miss (configurable fallback model per route)
Rate Limit Awareness
  • Detect 429 responses and Retry-After headers from providers
  • Preemptive throttling via token bucket per provider (RPM, TPM limits)
  • At 80% of limit: distribute overflow requests to secondary provider
  • Token bucket state synced across Gateway replicas via Redis
  • Dashboard showing current utilization vs configured limit per provider
Provider SLA Tracking & Alerting
  • Track uptime, latency, and error rate per provider over hourly, daily, and monthly windows
  • Compare measured performance against SLA targets
  • Alert on SLA breach with specific metrics and time window
  • Monthly SLA report for vendor management and contract negotiations
  • Cost-per-token correlated with quality metrics for provider ROI analysis
Success Metrics
  • Provider failover completes in <5 seconds
  • Zero user-visible 429 errors with preemptive throttling enabled
  • End-to-end availability ≥99.95% despite individual provider outages
  • Auto-failback within 2 minutes of provider recovery

Feature Gaps — What We Need

Comprehensive breakdown of every missing feature, organized by category and prioritized by business impact.

FG1. Prompt Management & Versioning P1
Why This Matters

Prompts are the primary interface to LLMs. Without versioning and management, teams lose reproducibility, cannot iterate safely, and have no way to measure which prompts perform best.

Features
  • Central catalog of prompt templates with name, description, model binding, owner, and tags. Searchable and filterable.
  • Full version history for every prompt with diff view between versions, author tracking, and changelog.
  • Support {{variable}} placeholders with type-safe parameter schemas (string, number, enum, JSON). Validate at save time.
  • Test prompts against any registered model. Side-by-side comparison of outputs. Adjustable temperature, top_p, max_tokens.
  • Promote prompts through dev → staging → production with optional approval gates. Track which version is active per environment.
  • Route configurable % of traffic between prompt versions. Collect quality metrics per variant. Statistical significance detection.
  • Track usage count, avg token cost, avg latency, error rate per prompt version. Cost projection for prompt changes.
Status: In Progress — being developed in parallel by an intern. Will be merged upon completion.
FG2. Evaluation Framework P1
Why This Matters

LLM outputs are non-deterministic. Without systematic evaluation, teams ship quality regressions, and degradation goes unnoticed until users complain.

Features
  • Upload and manage test datasets as input/expected output pairs. Support JSONL, CSV import. Version datasets alongside prompts.
  • Run prompts against datasets. Built-in scorers: exact match, BLEU, ROUGE, semantic similarity (embedding cosine), LLM-as-judge.
  • Side-by-side output comparison with thumbs up/down, Likert scale (1-5), and free-text feedback. Batch assignment to reviewers.
  • Automated alerts when eval scores drop below configurable threshold after a prompt or model change. Block deployment on regression.
  • Compare same prompt across multiple models/versions on identical dataset. Cost-normalized quality scores.
  • Run eval suite as a GitHub Action pipeline gate. Fail PR if quality regresses. Report eval results as PR comment.
  • Plugin system for domain-specific metrics: factuality checker, medical accuracy, legal compliance, code correctness.
Status: Maybe — not a current priority. May implement in a future phase.
FG3. Guardrails & Safety P2
Why This Matters

Production LLMs need input/output filtering to prevent prompt injection, toxic content, PII leakage, and policy violations.

Features
  • Detect and block prompt injection attempts, jailbreak patterns, PII in inputs. Configurable action: block, warn, log.
  • Filter toxic, harmful, or off-topic responses before reaching users. Toxicity classifier + keyword blocklist.
  • Define rules using regex, keyword lists, classifier scores. Apply per-model or globally. Version policies.
  • Score output groundedness against provided context for RAG scenarios. Flag low-confidence responses for review.
  • Automatically detect and mask PII (emails, phone numbers, SSNs, addresses) in inputs and outputs.
  • Dashboard showing block rates, violation types, false positive rates. Drill down by model, application, time range.
  • Bring your own classifier or model for domain-specific filtering. Standard gRPC interface for external guardrail services.
FG4. Tracing & Observability P0
Why This Matters

Current metrics cover GPU/infra only. Production debugging requires request-level tracing with full input/output visibility.

Features
  • End-to-end trace for every LLM call: input prompt, output response, latency breakdown, token counts, calculated cost.
  • Search by model, status, latency range, token count, user ID, application, time window.
  • Full request/response inspection with token breakdown, timing waterfall, and span tree.
  • Aggregate error patterns: rate limit hits, timeouts, provider errors. Root cause grouping and frequency analysis.
  • Configurable alerts on error rate, P99 latency, cost thresholds, throughput drops. Slack/webhook delivery.
  • Export traces to Jaeger, Datadog, Grafana Tempo via OTLP. Compatible with existing observability stacks.
FG5. Model Registry & Versioning P1
Why This Matters

Current registry is flat. Production needs versioned models with lineage tracking, model cards, and promotion workflows.

Features
  • Track multiple versions (v1, v2, fine-tuned variants). Each version has eval scores, deployment status, and metadata.
  • Visual graph: base model → fine-tune job → evaluation → deployment. Full traceability.
  • Structured metadata: training data summary, eval results, known limitations, license, intended use.
  • Side-by-side comparison of model versions on eval metrics, cost, latency, throughput.
  • Promote model versions through dev → staging → prod with approval gates.
  • Archive old versions with configurable retention policies. Cold storage for weights.
FG6. Autoscaling & Cost Management P0
Why This Matters

GPU resources are expensive. Manual replica management leads to over-provisioning or latency spikes. Autoscaling is essential for cost efficiency.

Features
  • Horizontal Pod Autoscaler rules based on queue depth, GPU utilization, or custom Prometheus metrics.
  • Scale idle deployments to 0 replicas after configurable inactivity timeout.
  • Cold-start on first request with configurable warm-up. Queue requests during scale-up.
  • Per-team/namespace GPU and memory quotas. Block deployments that exceed quota.
  • Estimated hourly/daily/monthly cost per deployment based on GPU type, count, and pricing.
  • Deploy on spot/preemptible GPUs with automatic fallback to on-demand.
FG7. Access Control & Governance P1
Why This Matters

Teams need role-based access to prevent unauthorized deployments and enforce approval workflows.

Features
  • Restrict teams to specific K8s namespaces and model subsets.
  • Require manager approval before deploying to production namespaces.
  • Searchable log of all actions: who deployed what, when, from which Git commit.
  • LLMOps API keys with fine-grained permission scopes.
  • Connect to Okta, Azure AD, Google Workspace. Map SSO groups to platform roles.
FG8. Multi-Cluster Management P2
Why This Matters

Enterprise deployments span multiple clusters and regions for high availability and data residency.

Features
  • Register and manage multiple K8s clusters with health monitoring and GPU inventory.
  • Deploy same model to multiple clusters with a single action.
  • Route requests to nearest healthy cluster based on geographic proximity.
  • Aggregated view: total GPUs, running deployments, error rates per cluster.
  • Automatic failover to secondary cluster on primary failure.
FG9. Notification & Integrations P1
Why This Matters

Platform events need to reach the right people through the right channels.

Features
  • Notify on deployment status changes, sync failures, alert triggers, approval requests.
  • Generic webhooks for all platform events. JSON payload with event type and metadata.
  • Escalate critical alerts to on-call rotation.
FG10. Batch Inference P2
Why This Matters

Many AI workflows require offline batch processing rather than real-time inference.

Features
  • Submit CSV/JSONL of prompts for offline processing. Select model, parameters, output format.
  • Priority queuing, pause/resume, retry failed items. Progress bar with ETA.
  • Download results as JSONL, CSV, or Parquet. Include token usage and cost per row.
  • Cron-based recurring batch jobs for daily report generation or data enrichment.

User Flows

Step-by-step workflows showing how users interact with the platform for common tasks.

Deploy a Model

  1. Navigate to Deploy page — Click “Deploy Model” from dashboard or sidebar
  2. Select Engine — Choose from vLLM, Ollama, SGLang, TGI, Whisper, Piper
  3. Configure — Set model path, GPU count, replicas, edit Helm values YAML
  4. Deploy — Submit creates K8s Deployment + Service via Helm chart rendering
  5. Monitor — Watch phase transition: Pending → Deploying → Running
  6. Validate — Check GPU utilization, throughput, and latency on Metrics page

Set Up GitOps

  1. Connect Repository — Enter GitHub org, repo name, branch, and deployment path
  2. Authenticate — Token encrypted with AES-256-GCM and stored in PostgreSQL
  3. Validate — Verify token has read/write access to the repository
  4. Initial Sync — Export current K8s deployments as YAML files to Git
  5. Configure Sync — Set poll interval or configure webhook for push-triggered sync
  6. Deploy via Git — Commit new deployment YAML → Push to Git → webhook fires → gateway syncs to K8s automatically

Add a Self-Hosted Provider with Load Balancing

  1. Create Provider — Add provider with name, base URL, API type, mark as self-hosted
  2. Set Credentials — Optionally set API key for the provider (encrypted at rest)
  3. Add Backends — Add multiple backend URLs with weights
  4. Discover Models — Click discover to auto-populate available models from endpoints
  5. Verify — View endpoint health status on Providers page

Investigate a Production Issue

  1. Receive Alert — Slack: “Error rate > 5% for openai/gpt-4 in last 15min”
  2. Search Traces — Filter traces by model=gpt-4, status=error, last 30 minutes
  3. Inspect — View full request/response, identify timeout or provider error
  4. Check Guardrails — Verify if input guardrails are blocking legitimate requests
  5. Review Evals — Check eval scores for current prompt vs last known good
  6. Remediate — Revert to previous prompt version or switch to backup model

Evaluate and Deploy a New Prompt

  1. Create prompt in registry — Write template with {{variables}}, assign to model
  2. Test in Playground — Try prompt with sample inputs, compare across models
  3. Run Evaluation — Select eval dataset, run against prompt, collect scores
  4. Human Review — Submit for human review → Assign batch of outputs to reviewers for quality assessment
  5. Stage — Deploy prompt version to staging for integration testing
  6. A/B Test — Route 10% traffic to new version, compare over 24 hours
  7. Promote — Promote to 100% after statistical significance confirmed

Import a New Model

  1. Open Import Wizard — Click “Import Model” from Model Registry page
  2. Select Source — Choose HuggingFace, S3/GCS, OCI Registry, or Git LFS
  3. Auto-Detect Metadata — System reads config.json and model card to pre-fill architecture, quantization, context length
  4. Configure Parameters — Review and adjust required/optional parameters. Validation runs in real-time
  5. Download & Validate — Model downloaded to staging PVC with progress bar. Checksum and format validation run automatically
  6. Test Inference — Ephemeral K8s Job runs 3 canary prompts. Results shown in wizard. Must pass to proceed
  7. Register — Model registered in catalog with all metadata, license info, and test results. Available for deployment

Handle a Model Failure & Recovery

  1. Alert Received — Notification: “Error rate > 10% for deployment llama-3-70b in namespace prod”
  2. View Incident Timeline — Open deployment detail → timeline view shows probe failures, metric spikes, and pod events
  3. Inspect Classification — Failure engine classified as “Permanent” based on OOM kill termination reason
  4. Auto-Rollback — System verified previous revision artifacts exist and initiated rolling update to last-known-good
  5. Verify Recovery — Confirm new pods healthy, error rate returned to baseline, canary probes passing
  6. Post-Mortem — Export incident timeline as JSON. Root cause: memory estimate was 5 GB below actual due to missing KV cache overhead

Technical Requirements

Performance, security, availability, and compliance targets for the platform.

Security

  • All sensitive data (credentials, tokens, PII) encrypted at rest.
  • All inter-service communication over mTLS. External traffic over TLS 1.3.
  • JWT for web sessions, API keys for programmatic access. Refresh token rotation.
  • Every state-changing action logged with actor, timestamp, and before/after state.
  • Audit log, RBAC, encryption, and access controls compatible with SOC 2.
  • All secrets encrypted (AES-256-GCM). API keys hashed (SHA-256). No plaintext in logs.

Scalability

  • Gateway Service, LLMOps API, Portal API all horizontally scalable behind load balancer.
  • Architecture supports multiple K8s clusters with federated control plane.
  • PostgreSQL read replicas for heavy read workloads (traces, metrics, audit logs).
  • Admission controller webhook evaluates GPU/memory quotas before pod creation.
  • Priority queue with preemption ensures critical workloads always get resources.
  • Burst capacity to cloud GPU providers when on-prem is exhausted.
  • GPU Inventory Agent (DaemonSet) reports NVML metrics per node at 10s intervals.

Observability

  • Handle high-throughput trace and span ingestion without data loss.
  • Hot storage for fast search. Cold storage (S3/GCS) for compliance and audit.
