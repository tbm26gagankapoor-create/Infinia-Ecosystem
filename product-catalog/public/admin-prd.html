F2. Metered Billing M3 · Apr 11

Automatic per-token billing with hourly usage aggregation via Stripe. Postpaid is not self-serve — it requires sales engagement, a signed SLA, and activation by an Infinia admin. Each organisation is allocated a credit limit by the admin.

  • Per-token billing
  • Hourly usage aggregation
  • Stripe integration
  • Sales-led activation (not self-serve)
  • SLA signature required
  • Per-org credit limit enforced
Activation Flow (Sales-Led)
  1. User clicks “Switch to Postpaid” in Billing settings → shown a Contact Sales prompt with email (sales@infinia.ai) and a Calendly booking link. No self-serve approval.
  2. Sales team qualifies the organisation and sends an SLA for signature (DocuSign or equivalent).
  3. Once SLA is signed, an Infinia admin activates postpaid for the organisation via the Admin Portal → A3. Org Postpaid & Credit Limits and sets the credit limit.
  4. Organisation owner receives email confirming postpaid is active, with the allocated credit limit displayed.
Billing Cycle Flow (Post-Activation)
  1. API usage generates billing events per request (input tokens + output tokens at model-specific rates).
  2. Usage aggregated hourly. Real-time estimates on dashboard (not billed until invoice).
  3. Credit limit enforced: at 80% of org’s credit limit, email alert sent to org owner and all admins. At 100%, API calls return 402 until next billing cycle resets or admin increases the limit.
  4. At end of billing period (monthly): invoice generated with line items per model.
  5. Stripe charges payment method on file, or customer pays via bank transfer. Invoice status: paid/pending/failed.
  6. Failed payment: retry 3 times over 7 days. After final failure, postpaid suspended; account restricted to prepaid only until resolved with sales.

A3. Org Postpaid & Credit Limits M3 · Apr 11 Admin Only

Infinia admin panel for activating postpaid billing per organisation, recording SLA status, and setting a credit limit that caps outstanding postpaid exposure.

  • List all orgs with postpaid status
  • Activate / deactivate postpaid per org
  • Set / update credit limit (dollar amount)
  • Record SLA signature status and date
  • Credit limit visible to org owner (read-only) in their Billing dashboard
  • 80% and 100% credit limit alerts to org owner + admins
  • API returns 402 when credit limit reached
Admin Flow
  1. Infinia admin navigates to Admin Portal → Organisations → Postpaid & Credit Limits. Sees table: Org Name, Plan, Postpaid Status (Inactive / Active / Suspended), SLA Status (Unsigned / Signed + date), Credit Limit, Current Period Usage.
  2. Admin selects an organisation. Clicks “Activate Postpaid”. Sets credit limit (e.g., $10,000) and confirms SLA is signed (records date).
  3. System updates org billing method to Postpaid. Org owner receives activation email with credit limit shown.
  4. Admin can update credit limit at any time (e.g., increase after first invoice paid). Change takes effect immediately.
  5. Admin can suspend postpaid (e.g., on failed payment after retries exhausted). Org reverts to prepaid; owner receives notification.
Error: attempting to activate without SLA date → validation error: “SLA signature date is required before activating postpaid.”
Org Owner View (read-only)
  1. Org owner navigates to Billing. Billing method card shows “Postpaid (Active)” and the credit limit allocated by admin.
  2. Current period usage shown as a progress bar against the credit limit.
  3. At 80% of credit limit: yellow warning banner + email to all org admins and owner.
  4. At 100% of credit limit: red banner + email. All API keys return 402 until the next billing cycle or admin increases the limit.
  5. Org cannot self-modify the credit limit — must contact sales or their account manager.

Technical Architecture

System Overview

The platform follows a layered architecture with clear ownership boundaries. All external traffic enters through CloudFlare, which handles CDN, DDoS protection, and edge caching before routing to the internal infrastructure.

Request Flow

User Portal / App
↓
CloudFlare (CDN + Edge)
↓
Envoy Proxy (ext_auth/tcp ↔ Control Service)
↓
Dynamic Forward Proxy → K8s GPU Cluster → Models

Envoy Proxy Integration

Envoy acts as the central API gateway with two extension points connecting to the Control Service:

ExtensionProtocolPurpose
ext_authTCPAuthentication & authorization — validates API keys (tf- prefix), checks rate limits, verifies org membership
ext_procgRPCRequest/response processing — token counting, usage metering, request transformation, billing event emission

GPU Cluster

Models run on a Kubernetes GPU cluster managed by a custom operator. The operator handles model deployment, scaling, health monitoring, and connects to GitHub for GitOps-driven model configuration. Inference requests reach models via Envoy's Dynamic Forward Proxy, which routes based on the requested model ID.
